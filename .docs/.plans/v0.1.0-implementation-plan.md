# Forge v0.1.0 Implementation Plan

> **Foundation — The Viewport**  
> *A cross-platform 2D CAD viewport with ECS-backed geometry, command-driven interaction, and a 60fps wgpu render pipeline.*

---

## Plan Overview

**Objective:** Build a native desktop 2D CAD viewport application with wgpu rendering, ECS geometry storage, command-line interaction (`LINE`, `CIRCLE`, `ARC`, `PLINE`), mouse/keyboard input, grid overlay, and egui-based UI chrome (status bar, command line, toolbar, property inspector).

### Step 2 — Geometry Types, Color, and Error Types

**Goal:** Implement `Point2D`, `BoundingBox2D`, `Color`, and `ForgeError` — the foundational data types used by every other module.

**Context Brief:**

`Point2D` (§5.1) is a CAD-grade f64 2D point with `new()` and `to_f32_array()` methods. `BoundingBox2D` (§5.1) is an axis-aligned bounding box with `min`/`max` fields, `is_empty()`, `center()`, and `union()` methods (handling empty boundary cases). `Color` (§10) is an RGBA f32 struct with `#[repr(C)]`, `bytemuck::Pod`/`Zeroable` derives for GPU upload, a `const fn from_hex(hex: u32)`, and const color constants (`WHITE`, `BLACK`, `GRAY_DARK`, `GRAY_MEDIUM`, `GRAY_LIGHT`). `ForgeError` (§10) is a `thiserror`-derived enum with `Gpu(String)`, `Surface(String)`, `Command(String)`, `Parse(String)`, and `Io(std::io::Error)` variants. It has `From<wgpu::Error>` and `From<wgpu::SurfaceError>` impls.

**Task List:**

### Step 3 — ECS Components & Resources

**Goal:** Define all ECS component types (`LineData`, `CircleData`, `ArcData`, `PolylineData`, `Renderable`, `Position`) and resource types (`CameraState`, `GridConfig`, `InputState`).

**Context Brief:**

ECS components (§5.2) are plain structs that implement `Send + Sync + 'static` (hecs 0.10 does not require a derive macro — any type satisfying these bounds is automatically a component). Key types:

- `Renderable` — marker struct (no fields)
- `Position(Point2D)` — placeholder for v0.2.0+ transforms
- `LineData { start, end: Point2D, color: Color, width: f32 }` — Copy
- `CircleData { center: Point2D, radius: f64, color: Color, width: f32 }` — Copy
- `ArcData { center: Point2D, radius: f64, start_angle, end_angle: f64, color: Color, width: f32 }` — Copy (angles in degrees)
- `PolylineData { vertices: Vec<Point2D>, closed: bool, color: Color, width: f32 }` — Clone (not Copy, heap-allocated)

ECS resources (§5.3) are singleton data structs:
- `CameraState` — `target: Point2D`, `zoom: f64`, `viewport_size: (u32, u32)`, `clear_color: Color`. Implements `screen_to_world(screen: (f32,f32)) -> Point2D`, `world_to_screen(world: Point2D) -> (f32,f32)`, `view_proj_matrix() -> Matrix4<f32>` with nalgebra's `Orthographic3`. Clones.
- `GridConfig` — `visible: bool`, `major_spacing, minor_spacing: f64`, `major_color, minor_color, axis_color: Color`. Has `Default` impl with visible=true, spacing 100/10, gray colors.
- `InputState` — `mouse_screen: (f32,f32)`, `mouse_world: Point2D`, `left_down, middle_down, right_down, shift, ctrl, alt: bool`. Derives `Default`.

**Task List:**

1. **Create `src/ecs/components.rs`** — All 6 component structs with appropriate derives. Add the design note comment for `Position`. Add the hecs note comment explaining no derive macro needed.

2. **Create `src/ecs/resources.rs`** — `CameraState`, `GridConfig`, `InputState` structs. Implement `CameraState` methods: `screen_to_world`, `world_to_screen`, `view_proj_matrix`. Implement `Default` for `GridConfig`. Implement `Default` for `InputState`.

   Key implementation details for `CameraState`:
   - `view_proj_matrix()` uses `nalgebra::Orthographic3::new(left, right, top, bottom, -1.0, 1.0)` with bounds computed from `target` and `zoom`
   - `screen_to_world()` normalizes screen coords to [-1,1] with Y flip, then inverts the projection
   - `world_to_screen()` is the forward transform
   - Both methods guard against zero viewport size and zero zoom

3. **Update `src/ecs/mod.rs`** — `pub mod components; pub mod resources; pub use components::*; pub use resources::*;`

**Dependencies:** Step 2 (Point2D, Color)

### Step 4 — Command Trait, CommandState, and nom v8 Parser

**Goal:** Define the `Command` trait, `CommandInput`/`CommandResult` enums, `CommandState` struct, `PreviewEntity`, and the complete nom v8 parser for all four commands (LINE, CIRCLE, ARC, PLINE).

**Context Brief:**

The command system (§6.1) defines:
- `Command` trait with methods `name()`, `prompt()`, `steps_remaining()`, `on_input()`, `on_cancel()`, `preview()`
- `CommandInput` enum: `Point(Point2D)`, `Text(String)`, `Distance(f64)` (dead_code), `Angle(f64)` (dead_code), `Cancel`, `Confirm`
- `CommandResult` enum: `Continue`, `Complete`, `Error(String)`, `Cancelled`
- `CommandState` struct: `active: Option<Box<dyn Command>>`, `history: Vec<String>`, `buffer: String`, `last_error: Option<String>`, `pending_dispatch: Option<String>`
- `PreviewEntity` struct: `points: Vec<Point2D>`, `color: Color`, `width: f32`

The parser (§6.2) uses nom v8's function-based API with `Parser` trait and `.parse()` method calls. Key functions:
- `parse_point(&str) -> IResult<&str, Point2D>` — parses "10,20" style coordinates
- `parse_command(&str) -> IResult<&str, ParsedCommand>` — dispatches on command name
- `ParsedCommand` enum with `Line(LineArgs)`, `Circle(CircleArgs)`, `Arc(ArcArgs)`, `Polyline(PolylineArgs)`
- Each `*Args` struct uses `Option` fields for inline arguments

Important parser details:
- Case-insensitive command names with aliases (LINE/L, CIRCLE/C, ARC/A, PLINE/PL)
- Whitespace after command name is optional (`opt(space1)`) to allow bare "LINE"
- `space1` after name prevents "LINE0,0" false matches
- PLINE close token "C" requires whitespace or EOF after it to avoid matching "C10,20" as a vertex
- PLINE returns error if no vertices collected
- ARC start_angle and end_angle are conditional on previous arg presence

**Task List:**

1. **Create `src/commands/mod.rs`** — Define `Command` trait, `CommandInput`, `CommandResult`, `CommandState`, `PreviewEntity`. Implement `Default` for `CommandState`. No `Send + Sync` bounds on `Command` trait (single-threaded).

2. **Create `src/commands/parser.rs`** — Implement full nom v8 parser matching the spec exactly:
   - Import from `nom::` correctly: `IResult`, `Parser`, `branch::alt`, `bytes::complete::tag_no_case`, `character::complete::{char, space0, space1}`, `combinator::{map, opt}`, `number::complete::float`, `sequence::{preceded, tuple}`
   - Define `ParsedCommand`, `LineArgs`, `CircleArgs`, `ArcArgs`, `PolylineArgs`
   - Implement `parse_point()` using `tuple((float, preceded(space0, char(',')), preceded(space0, float)))`
   - Implement `parse_command()` with alt matching all 8 name variants
   - LINE branch: optional start point, optional end point
   - CIRCLE branch: optional center, optional radius
   - ARC branch: cascading optional center → radius → start_angle → end_angle
   - PLINE branch: loop collecting points until C close token or no more valid points

### Step 5 — LINE Command Implementation

**Goal:** Implement `LineCommand` using the buffer-then-commit design pattern.

**Context Brief:**

The LINE command (§6.3) uses a buffer-then-commit pattern:
- Points accumulate in `pending_points: Vec<Point2D>` (not spawned into ECS until confirmed)
- On `Complete` (Enter), all line segments from the buffer are spawned as `(LineData, Renderable)` pairs
- On `Cancel` (Escape), the buffer is dropped with no cleanup needed
- `preview()` returns empty vec (rubber-band deferred to v0.2.0+)
- Text input "U" undoes the last point
- `steps_remaining()` returns 0 when ≥2 points accumulated (enables auto-commit for inline commands like "LINE 0,0 100,100")

The specually warns against prematurely spawning entities into the ECS (Rev 3 H3 rewrote this to use buffer-then-commit). The `on_input` method must use `CommandInput::Confirm` to trigger the commit path.

   - `prompt()` — "Specify first point:" or "Specify next point or [Undo]:"
   - `steps_remaining()` — `2 - pending_points.len()` or 0 if ≥2
   - `on_input()` — handle `Point`, `Text("U")`, `Confirm` (spawns segments), `Cancel`
   - `on_cancel()` — clear buffer
   - `preview()` — return empty vec

3. **Create `src/commands/circle_cmd.rs`** — Stub only:

### Step 6 — Input System (Mapper + Actions)

**Goal:** Implement `InputMapper` that translates winit `WindowEvent`s into `InputAction` values, and the `InputAction` enum.

**Context Brief:**

The input system (§8.1) maps winit events to application actions:
- `InputMapper` holds `state: InputState` and `last_mouse_screen: (f32, f32)`
- `handle_event(&mut self, event: &WindowEvent, camera: &CameraState) -> Vec<InputAction>`
- Maps `CursorMoved` → `InputAction::MouseMoved(Point2D)` (updates `InputState.mouse_screen` and `mouse_world`)
- Maps `MouseInput` (Pressed) → `Click`, sets `left_down`/`middle_down`/`right_down`
- Maps `MouseInput` (Released) → clears button states
- Maps `MouseWheel` → `InputAction::Zoom`
- Maps `KeyboardInput` (Pressed) → `Cancel` (Escape), `Confirm` (Enter), `Text(char)` (single chars), modifier key state (`shift`, `ctrl`, `alt`)
- Includes pan handling: when `middle_down`, computes delta from `last_mouse_screen` to current and produces `InputAction::Pan`

`InputAction` enum: `MouseMoved(Point2D)`, `Click(Point2D)`, `Pan(f64, f64)`, `Zoom(f64, Point2D)`, `Cancel`, `Confirm`, `#[allow(dead_code)] Text(char)`, `#[allow(dead_code)] CommandText(String)`.

Important notes from the spec:
- `Text(char)` is dead code in v0.1.0 — egui swallows keyboard when its text field has focus
- `CommandText(String)` is defined but never produced by `handle_event` — it's reserved for future direct keyboard command input
- The alloc-per-event overhead of `Vec::new()` is acceptable in v0.1.0
- winit 0.30 `PhysicalPosition<f64>` field types should be verified at compile time

**Task List:**

1. **Implement `src/input/mod.rs`**:

   - `handle_event()` method with full event matching
   - `InputAction` enum with all variants and `#[allow(dead_code)]` annotations

   The method must handle pan tracking: when `middle_down` is true, compute dx/dy from `last_mouse_screen` to current `state.mouse_screen` and emit `InputAction::Pan`.

### Step 10 — Entity Renderer

**Goal:** Implement `EntityRenderer` with per-type WGSL shaders, staging buffers, and batching logic for line, circle, arc, and polyline entities.

**Context Brief:**

The entity renderer (§7.4) renders all ECS entities with `Renderable` components:
- **Batching:** All entities of the same type are packed into one vertex buffer per frame → one draw call per entity type
- **Line Rendering:** Each `LineData` → 2 vertices, `LineList` topology
- **Circle Rendering:** Each `CircleData` → 64-segment line strip approximation, `LineStrip` topology
- **Arc Rendering:** Each `ArcData` → proportional segments based on sweep angle, `LineStrip`. Angles converted from degrees to radians for GPU.
- **Polyline Rendering:** Open → `LineStrip`, Closed → `LineList` (with closing segment)
- **Entity vertex format:** `{position: [f32; 2], color: [f32; 4]}` — shared across all types
- **Staging buffers:** Separate per type (`line_staging`, `circle_staging`, `arc_staging`, `polyline_staging`), each with capacity tracking (`*_staging_capacity`). Initial size: `INITIAL_STAGING_SIZE = 32768` bytes. Resize strategy: double capacity if exceeded.
- **WGSL shaders:** All use the same `CameraUniform` from `shared.wgsl`. Pipeline uses `LineList` or `LineStrip` primitive topology.

**Task List:**

1. **Create `src/render/shaders/line.wgsl`** — Same vertex/fragment structure as grid shader, using `CameraUniform` from shared WGSL:
   ```wgsl
   // Import shared or duplicate struct
   struct VertexInput {
       @location(0) position: vec2<f32>,
       @location(1) color: vec4<f32>,
   };
   struct VertexOutput {
       @builtin(position) clip_position: vec4<f32>,
       @location(0) color: vec4<f32>,
   };
   @group(0) @binding(0) var<uniform> camera: CameraUniform;
   @vertex fn vs_main(...) -> VertexOutput { ... }
   @fragment fn fs_main(...) -> @location(0) vec4<f32> { ... }
   ```

2. **Create `src/render/shaders/circle.wgsl`** — Same structure; note that circle tessellation is done on CPU side.

3. **Implement `EntityRenderer::new()`** in `src/render/entity_renderer.rs`:
   - Load 4 WGSL shaders via `include_str!()`
   - Create 4 render pipelines (line: LineList, circle: LineStrip, arc: LineStrip, polyline: LineList)
   - All use `camera_bind_group_layout` for group(0)
   - Create 4 staging buffers, each 32KB initially
   - Set all capacity fields to `INITIAL_STAGING_SIZE`

4. **Implement `EntityRenderer::render()`**:
   - Query ECS for each entity type using hecs queries:
     ```rust

     // ... similar for Circle, Arc, Polyline
     ```

   - For lines: iterate, generate 2 vertices per entity (start, end)
   - For circles: iterate, generate 64 vertices per circle (line strip approximation)
   - For arcs: iterate, generate proportional segments (sweep_angle/360 * 64, min 8)
   - For polylines: iterate vertices, add closing segment if `closed`
   - Write to staging buffers (resize by 2× if capacity exceeded)
   - Begin render pass for entities (load = `LoadOp::Load`, draw on top of grid)
   - For each type: set pipeline, bind camera bind group, set vertex buffer, draw
   - 4 separate render passes, one per entity type

5. **Add degree-to-radian conversion note** in arc rendering: `angle * std::f64::consts::PI / 180.0` before computing vertex positions.

## Anti-Pattern Checklist

During execution, watch for these spec-enumerated anti-patterns:

| Anti-Pattern | Where It Bites | Guard |
|---|---|---|
| Speculative generics | Command trait, renderers | No type params unless required by a concrete v0.1.0 use case |
| Premature optimization | Entity batching | Single buffer per type, one draw call — no instancing |
| Over-engineering | Stub modules | `todo!()` is correct for deferred features |
| Cross-step contamination | Unused imports from future steps | Each step only uses types from prior steps |
| Missing verification | No test for new logic | Every non-trivial function needs a test |
| `f32` == `Eq` | Color derives | Rev 11 C1: Color derives `PartialEq`, NOT `Eq` |
| Double view translation | Camera matrix | Orthographic3 bounds encode camera position; no separate view matrix |
| Wrong nom import path | Parser | nom v8: `number::complete::float` (not `character::complete::float`) |
| Wrong wgpu API | RenderState | wgpu 0.29: `get_current_texture()` returns `Result`, no `memory_hints` field |
| Wrong winit API | Input/App loop | winit 0.30: `ApplicationHandler`, `PhysicalPosition<f64>`, `WindowAttributes::default()` |
